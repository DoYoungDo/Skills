# Agent Task Workflow

用于规范 AI agent 执行任务时的通用工作流。核心目标是让 agent 先对齐需求，再把任务拆成可快速实现和验证的小切片，通过 TDD、验证、checkpoint 和恢复循环持续取得正向进展。

## 目标

- 在开始执行前确认目标、范围、验收标准和风险点。
- 将复杂任务拆成快速实现、快速验证的小任务，避免长时间执行导致上下文丢失和结果失真。
- 对代码行为变更优先采用 TDD，让测试驱动实现。
- 以测试、构建、类型检查、lint 或其他明确验证方式定义完成标准。
- 在授权工作区内，对每个正向进展形成 checkpoint 提交。
- 出现负进展时，安全回滚当前切片并重新进入循环。

## 适用场景

适用于所有项目类型，不绑定具体语言、框架或技术栈。

优先适用：

- 新功能开发。
- bug 修复。
- 重构。
- 代码生成或代码修改。
- 多步骤排查和修复。
- 需要验证、提交或持续推进的工程任务。

轻量适用：

- 文档修改。
- 配置说明。
- 代码解释。
- 简单命令执行。
- 纯调研或只读分析。

## 约束等级

- `MUST`：必须遵守，除非用户明确覆盖，且不会违反安全边界。
- `SHOULD`：默认应遵守，可根据任务复杂度和上下文调整。
- `MAY`：允许采用，用于提升质量、效率或可追踪性。

## 核心工作流

标准正向流程：

```text
Align -> Contract -> Slice -> Test First -> Implement -> Verify -> Checkpoint -> Loop
```

失败恢复流程：

```text
Detect Negative Progress -> Roll Back Current Slice -> Analyze -> Re-slice -> Retry
```

连续失败退出流程：

```text
Stop -> Summarize Attempts -> Report Blocker -> Ask For Direction
```

## Task Contract

复杂任务开始前，agent SHOULD 和用户对齐一个轻量任务契约。任务越复杂、风险越高，越应该显式输出并等待确认。

Task Contract 包含：

- `Goal`：要达成什么。
- `Scope`：允许修改、读取或操作哪些范围。
- `Out of Scope`：明确不做什么。
- `Acceptance`：怎样算完成。
- `Verification`：用什么方式验证。
- `Checkpoint`：是否在授权工作区内提交正向进展。
- `Rollback`：负进展时允许如何恢复。

简单、低风险、信息充分的任务 MAY 不显式输出完整 Task Contract，但 agent 仍 SHOULD 在内部确认目标、范围和验证方式。

## 需求对齐规则

- `MUST` 在需求存在多种合理解释、关键约束缺失或结果不可逆时先向用户确认。
- `MUST` 在涉及删除文件、数据迁移、大规模重构、生产配置、安全凭据、外部服务或破坏性操作时先确认。
- `SHOULD` 在开始复杂任务前给出方案，让用户确认执行路径。
- `SHOULD` 明确当前任务的验收标准，而不是只理解为“把代码写完”。
- `MAY` 对低风险实现细节基于项目上下文自行决策，并在结果中说明。

## 小任务切片规则

- `SHOULD` 将复杂任务拆成能快速实现、快速验证的小任务。
- `SHOULD` 以 3-5 分钟为参考粒度，但不把时长作为硬性限制。
- `MUST` 避免长时间执行一个不可验证的大任务。
- `MUST` 为每个切片定义明确验证方式。
- `SHOULD` 每个切片只解决一个可描述、可验证的问题。
- `MAY` 对极简单任务跳过显式切片，直接执行并验证。

切片应优先满足：

- 可以独立说明目标。
- 可以快速验证结果。
- 失败时可以安全回滚。
- 不依赖大量隐含上下文。
- 完成后能形成正向进展。

## TDD 工作流

- `SHOULD` 对代码行为变更使用 TDD。
- `MUST` 对 bug fix、新功能和重构优先考虑 TDD。
- `SHOULD` 先为当前切片写最小失败测试，再实现代码。
- `SHOULD` 实现最小代码，让当前测试和相关已有测试通过。
- `MUST` 不为了通过测试而删除测试、跳过测试、降低断言、mock 掉核心逻辑或隐藏错误。
- `MUST` 不伪造测试、构建或命令结果。
- `MUST` 在不适合自动化测试时说明原因，并给出替代验证方式。

TDD 循环：

```text
Red -> Green -> Refactor -> Verify
```

- `Red`：新增或定位一个能证明问题或需求的失败测试。
- `Green`：写最小实现让测试通过。
- `Refactor`：只在必要时整理本轮改动，不做无关重构。
- `Verify`：运行当前切片相关验证，确认没有回归。

## 验证规则

- `MUST` 将“验证通过”作为代码任务完成标准，而不是只把代码生成完成视为完成。
- `SHOULD` 优先运行项目已有测试、typecheck、lint、build 或针对性验证命令。
- `SHOULD` 优先选择能覆盖当前切片的最小验证命令，必要时再扩大验证范围。
- `MUST` 在验证失败时说明失败命令、关键错误和是否可能由当前改动引起。
- `MUST` 在无法验证时说明原因、风险和可选的后续验证方式。
- `MAY` 对无法自动化验证的任务使用 smoke test、手动验证清单或静态检查替代。

验证优先级：

1. 项目已有的针对性测试。
2. 当前切片新增或修改的最小测试。
3. 相关模块测试。
4. 类型检查、lint、构建。
5. smoke test 或手动验证清单。

## 正向进展与 Checkpoint

正向进展必须同时满足：

- 当前切片目标达成。
- 当前切片验证通过，或已有明确替代验证结论。
- 未引入已知回归。
- 改动范围可解释，且没有明显偏离 Task Contract。

Checkpoint 规则：

- `MUST` 在用户允许 agent 操作的工作区内，对每个正向进展直接创建 checkpoint 提交。
- `MUST` 在提交阶段使用 `code-commit` skill 的规则处理提交信息、提交范围、敏感风险和自动化提交流程。
- `MUST` 不重复定义或覆盖 `code-commit` 的具体提交规范。
- `MUST` 不默认 push，除非用户明确要求。
- `MUST` 不默认 amend，除非用户明确要求。
- `SHOULD` 在每个 checkpoint 后更新当前进度，明确下一切片。

如果用户没有允许 agent 操作当前工作区，agent MUST 不自动提交，只能汇报 checkpoint 状态并请求授权。

## 负进展与恢复循环

以下情况视为负进展：

- 新增测试无法按预期失败或无法证明需求。
- 测试从通过变为失败。
- 已有行为出现回退。
- 实现偏离用户目标或 Task Contract。
- 改动范围失控，开始牵连无关模块。
- 为通过测试而弱化验证质量。
- 验证无法继续，且原因来自当前切片改动。

恢复规则：

- `SHOULD` 在能明确识别本轮改动边界时，自动回滚当前切片。
- `MUST` 回滚后重新分析原因，必要时重新切片。
- `MUST` 同一切片连续 3 次负进展后暂停执行，汇报尝试过的方案、失败原因和可选下一步。
- `MUST` 不无限循环尝试同一失败路径。
- `SHOULD` 每次失败后缩小切片或调整验证方式，而不是扩大改动范围。

## 回滚安全边界

- `MUST` 只回滚 agent 当前切片引入的改动。
- `MUST` 不回滚用户已有改动、其他 agent 的并发改动或未确认来源的变更。
- `MUST` 在无法区分本轮改动和外部改动时暂停并询问用户。
- `MUST` 不执行破坏性 git 操作，例如 `git reset --hard`、强制覆盖、删除未确认文件，除非用户明确要求并确认风险。
- `MUST` 不改写提交历史，除非用户明确要求。
- `SHOULD` 优先通过补丁级撤销、精确编辑或还原当前切片文件片段完成回滚。

## 用户确认边界

以下操作 `MUST` 先确认，除非用户已经在当前任务中明确授权相同范围：

- 删除文件或目录。
- 大规模批量替换。
- 数据库迁移、数据删除或数据修复。
- 大规模重构或跨模块架构调整。
- 安装、升级或移除依赖。
- 修改生产配置、部署配置或凭据相关文件。
- 执行破坏性命令。
- push 到远端仓库。
- 修改提交历史。

提交 checkpoint 的确认边界由工作区授权决定：用户允许 agent 操作当前工作区时，正向进展后可以直接提交；提交过程仍 MUST 遵循 `code-commit`。

## 与其他 Skills 的协作

- 当任务进入 git 提交阶段，或用户要求生成提交信息、自动提交代码时，`MUST` 使用 `code-commit` skill。
- `agent-task-workflow` 只规定任务推进、验证、checkpoint 和恢复流程，不重复定义具体提交信息格式。
- 当其他 skill 提供更具体的领域规则时，`SHOULD` 同时遵循领域 skill 和本 skill。
- 如果领域 skill 与本 skill 冲突，`MUST` 优先遵守安全边界、用户明确指令和更具体的领域规则。

## 非代码任务例外

非代码任务可以不强制 TDD，但仍应保持可验证和可追踪。

- 文档任务 `SHOULD` 验证内容完整性、链接、示例命令和术语一致性。
- 配置任务 `SHOULD` 验证格式、加载路径和兼容性。
- 调研任务 `SHOULD` 输出依据、限制和未验证信息。
- 简单问答任务 MAY 直接回答，不需要 Task Contract、切片或 checkpoint。
- 只读分析任务 `MUST` 不修改文件，除非用户明确转为实现任务。

## 禁止行为

- 不跳过需求对齐直接进行高风险或大范围修改。
- 不长时间执行不可验证的大任务。
- 不生成大量未经验证的代码。
- 不伪造测试、构建、命令或检查结果。
- 不为了通过测试而删除、跳过或弱化测试。
- 不修改无关文件或进行无关重构。
- 不擅自 push。
- 不擅自修改提交历史。
- 不执行破坏性操作。
- 不回滚用户已有改动或并发改动。
- 不重复定义 `code-commit` 已经规定的提交细节。

## 输出规范

执行中输出 SHOULD 简洁，重点说明新发现、阻塞、方案变化或验证结果，不重复叙述 routine 操作。

最终输出根据任务类型调整：

- 简单任务：直接说明结果。
- 代码修改任务：说明改了什么、关键文件、验证命令和结果、checkpoint 状态。
- 失败或受阻任务：说明失败步骤、已尝试方案、关键错误、是否已回滚和下一步选择。
- review 类任务：优先输出问题和风险，再输出总结。

建议格式：

```text
结果：完成了什么。
改动：关键文件和原因。
验证：运行了什么，结果如何。
Checkpoint：是否已提交，提交信息或状态。
风险：剩余问题或未验证内容。
下一步：必要时给出选择。
```

## 示例用法

用户：

```text
修复登录接口在 token 过期时报 500 的问题
```

行为：先确认或推断验收标准，定位相关测试和接口实现；为 token 过期场景补充最小失败测试；实现最小修复；运行相关测试；通过后按 `code-commit` 创建 checkpoint。

用户：

```text
重构这个模块，让结构更清晰
```

行为：先对齐目标、范围和不改变行为的验收标准；拆分为小切片；优先增加 characterization tests；每个切片保持行为不变并验证；正向进展后提交 checkpoint。

用户：

```text
帮我新增一个导出 CSV 的功能
```

行为：先确认导出字段、格式、触发入口和验收标准；切出最小功能路径；先写导出格式测试；实现最小功能；验证通过后提交 checkpoint，再继续处理边界场景。

用户：

```text
把所有旧字段批量替换成新字段
```

行为：这是高风险批量操作，必须先确认范围、兼容策略、验证方式和回滚方式；未经确认不得直接批量修改。

用户：

```text
解释一下这个函数的作用
```

行为：这是只读分析任务，不需要 TDD、切片或 checkpoint；直接阅读相关上下文后回答。
