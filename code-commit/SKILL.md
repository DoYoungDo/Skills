# Code Commit

用于根据当前代码改动生成准确、简洁、中文的 Conventional Commits 提交信息。只有在用户明确授权提交时，才执行暂存、提交和提交后验证。

## 目标

- 根据 git diff 生成一个最佳中文提交信息。
- 提交信息必须符合 Conventional Commits。
- 提交时必须参考最近几次提交风格，在不违反本规范的前提下保持一致。
- 用户明确授权后，可以完成检查改动、暂存、提交和提交后状态验证。
- 提交信息末尾必须完全照写并换行追加 `AI-assisted-commit`，仅表示提交过程由 AI 辅助完成，不表示代码由 AI 编写或修改。

## 提交格式

优先使用：

```text
<type>(<scope>): <中文标题>

<body>

<footer>
AI-assisted-commit
```

`scope` 可选。无法可靠推断时省略：

```text
<type>: <中文标题>

AI-assisted-commit
```

破坏性变更同时支持 `!` 和 `BREAKING CHANGE:`：

```text
feat(api)!: 调整配置加载接口

BREAKING CHANGE: 旧的配置字段不再支持。

AI-assisted-commit
```

## 支持的 Type

- `feat`：新增功能、用户可见能力、接口能力或命令能力。
- `fix`：修复缺陷、错误行为、异常、崩溃或边界问题。
- `docs`：文档、README、指南或说明文字变更。
- `style`：格式、空白、排序、lint 修复等不影响逻辑的变更。
- `refactor`：重构，既不新增功能，也不修复缺陷。
- `perf`：性能优化、减少开销、提升速度或降低资源占用。
- `test`：新增或修改测试。
- `build`：构建系统、依赖、打包、编译配置变更。
- `ci`：持续集成 workflow、流水线脚本、发布流程变更。
- `chore`：维护类变更，且不适合以上类型。
- `revert`：回滚历史提交。

## Type 判断规则

- 按改动意图选择 type，不要只按文件类型判断。
- 多种 type 都适用时，选择最能表达主要目的的 type。
- 修复用户可见错误优先使用 `fix`，即使同时调整了测试或重构。
- 新增能力优先使用 `feat`，即使同时包含配置或文档变更。
- 只有行为不变的结构调整才使用 `refactor`。
- 无法判断主要意图时，先询问用户，不要臆测。

## Scope 推断规则

`scope` 可选，只有在能可靠推断时使用。

推断优先级：

1. 主要目录名，例如 `compiler`、`server`、`docs`、`cli`。
2. 包名、workspace 名、Go package、npm package 或模块名。
3. 主要影响的功能域，例如 `auth`、`router`、`config`。
4. 单一文件明显对应的模块名。

以下情况省略 `scope`：

- 改动横跨多个无明显主次的模块。
- 无法可靠判断模块边界。
- scope 显得牵强或过度具体。
- 提交是全局维护类改动。

## 标题规则

- 标题必须使用中文。
- 不强制长度，但必须清晰、简洁、准确。
- 优先使用动宾结构。
- 聚焦改动目的、行为变化或影响。
- 避免空泛表达，例如“更新代码”“修改文件”“优化逻辑”。
- 避免机械罗列文件名或实现细节，除非实现细节就是提交重点。

示例：

```text
feat(cli): 支持自动生成中文提交信息
fix(config): 修复空配置导致启动失败的问题
docs: 补充提交规范说明
refactor(parser): 简化类型推断流程
chore: 更新依赖锁文件
```

## Body 和 Footer 规则

简单改动只写标题和 `AI-assisted-commit`，不生成 body。

需要 body 的情况：

- 改动包含多个相关点，标题无法完整表达。
- 有行为变化、兼容性影响或迁移说明。
- 有重要实现取舍、限制或背景。
- 涉及安全、权限、数据迁移或配置变更。
- 涉及破坏性变更。
- 用户明确要求详细提交信息。

body 使用中文，说明改动原因、影响范围和必要背景。不要重复 diff 内容，不要机械罗列文件清单。

破坏性变更必须使用 `!`，并在 footer 中提供 `BREAKING CHANGE:` 说明。

`AI-assisted-commit` 必须位于提交信息末尾。若存在 `BREAKING CHANGE:`，先写 `BREAKING CHANGE:`，再空一行追加 `AI-assisted-commit`。

## 用户授权边界

仅生成提交信息的请求，不得执行 `git add` 或 `git commit`。

明确授权提交的表达包括：

- “帮我提交”
- “生成提交信息并提交”
- “自动完成提交”
- “提交全部改动”
- “commit 这些改动”

不明确授权提交的表达包括：

- “帮我写个提交信息”
- “这个改动应该怎么提交”
- “看看提交信息怎么写”

## 提交范围规则

- 已暂存文件默认属于提交范围。
- 用户要求“提交全部改动”时，已跟踪的未暂存改动默认纳入。
- 未跟踪文件默认不加入。
- 用户要求“提交全部改动”且存在未跟踪文件时，必须列出未跟踪文件并等待确认。
- 只有用户明确确认后，才加入未跟踪文件。
- 疑似临时文件、日志、构建产物、缓存文件应提示风险，不要默认加入。

## 敏感风险规则

提交前必须检查敏感文件和疑似密钥。

需要警告确认的情况：

- `.env`、`.env.*`
- 路径或文件名包含 `credentials`、`secret`、`token`、`key`、`private`
- 证书或私钥文件，例如 `.pem`、`.key`、`.p12`
- diff 中包含疑似 API key、访问令牌、私钥、证书内容
- 认证配置、生产环境配置、云服务凭据

发现敏感风险时：

- 明确列出风险文件或风险类型。
- 暂停提交。
- 请求用户确认是否继续。
- 用户明确确认后允许继续。
- 用户未确认时不得提交。

## 验证规则

- 自动提交前默认不运行验证命令。
- 如果用户指定验证命令，必须在提交前运行。
- 验证成功后继续提交。
- 验证失败默认阻断提交。
- 只有用户明确表示强制提交时，才允许在验证失败后继续。

强制提交必须是明确表达，例如：

- “验证失败也提交”
- “强制提交”
- “不用管测试失败，继续提交”

## 自动化提交流程

当用户明确授权自动提交时，按以下流程执行：

1. 检查 git 状态，识别 staged、unstaged、untracked。
2. 查看 staged 和 unstaged diff，理解实际改动。
3. 查看最近几次提交信息，参考仓库风格。
4. 确定提交范围；未跟踪文件必须确认后才加入。
5. 检查敏感文件和疑似密钥。
6. 如有敏感风险，警告并暂停，等待用户确认。
7. 如果用户指定验证命令，先运行验证。
8. 验证失败则阻断，除非用户明确强制继续。
9. 根据主要改动选择 type，可靠时推断 scope。
10. 生成一个最佳中文 Conventional Commits 提交信息。
11. 在提交信息末尾追加 `AI-assisted-commit`。
12. 暂存确认范围内的文件，不加入未确认的 untracked 文件。
13. 执行 `git commit`，不默认跳过 hooks。
14. 执行提交后状态检查。
15. 返回提交哈希、提交信息和剩余工作区状态摘要。

## 禁止行为

- 不在未授权时执行提交。
- 不自动加入未跟踪文件。
- 不在敏感风险未确认时提交。
- 不默认运行验证命令。
- 不默认 push。
- 不修改 git config。
- 不执行破坏性 git 操作。
- 不使用交互式 git 命令。
- 不跳过 hooks，除非用户明确要求。
- 不自动 amend。

## 输出规范

只生成提交信息时，输出一个最佳提交信息，并简要说明判断依据。

自动提交成功后，返回：

- 提交哈希。
- 实际提交信息。
- 是否有剩余未提交改动。
- 被排除或仍需处理的未跟踪文件。

自动提交失败时，返回：

- 失败步骤。
- 关键错误信息。
- 工作区是否已被暂存改动影响。
- 推荐的下一步处理方式。

## 示例用法

用户：

```text
帮我为当前改动生成提交信息
```

输出：

```text
feat(cli): 支持生成中文提交信息

AI-assisted-commit
```

用户：

```text
提交全部改动
```

行为：检查 diff、参考最近提交风格、确认未跟踪文件、检查敏感风险、生成提交信息并提交。

用户：

```text
用 npm test 验证后提交
```

行为：提交前运行 `npm test`；成功后提交，失败则默认阻断。

用户：

```text
这次是破坏性变更，帮我提交
```

输出格式示例：

```text
feat(api)!: 调整配置加载接口

BREAKING CHANGE: 旧的配置字段不再支持。

AI-assisted-commit
```
